Migration `supabase/migrations/20261021120000_wiz_billing.sql` (rollback `supabase/rollbacks/20261021120000_wiz_billing.down.sql`); code `lib/billing.js`.
Needs the foundation, career and privacy migrations first. **The paid gate is ON by default**; only `WIZ_BILLING_GATE=off` disables it (legacy test fixtures).

## Environment (template — no defaults, no price is built in)

```
STRIPE_SECRET_KEY=sk_test_...            # mode (test|live) is read from the prefix; never log or commit
STRIPE_WEBHOOK_SECRET=whsec_...          # signing secret of the endpoint below
WIZ_STRIPE_PRODUCT_ID=prod_...           # owner-approved WIZ product
WIZ_STRIPE_PRICE_ID=price_...            # owner-approved recurring price
WIZ_STRIPE_PRICE_AMOUNT=<minor units>    # verified against Stripe before purchase is offered
WIZ_STRIPE_PRICE_CURRENCY=<iso lower>    # e.g. the approved currency
WIZ_STRIPE_PRICE_INTERVAL=month|year
WIZ_BILLING_RETURN_URL=https://<allowlisted app origin>/<path>   # checkout success/cancel + portal return (must be on CORS_ORIGINS)
WIZ_BILLING_ERASURE_POLICY=block|cancel  # default block — see "Owner decisions"
```
Any missing/malformed piece, or a price that does not match Stripe's own record (amount, currency, interval, product, active, mode), leaves **purchase off**:
`GET /billing` says so (`purchase_available:false`, reason `not_configured|price_unverified`) and Checkout returns 503. Account, privacy, Terms, consent, history,
export and erasure keep working. The test suite uses a **synthetic fixture price** (`test/helpers/fake-stripe.js`) that is not a WIZ price.

## Routes (all under `/api/v1`)

| Route | Auth | Notes |
|---|---|---|
| `GET /billing` | user | `{ gate, mode, purchase_available, purchase_unavailable_reason, entitled, status, paid_through, cancel_at_period_end, can_manage, reconciled_at }` |
| `POST /billing/checkout` | user | body ignored. Serialised per owner; customer created with a stable idempotency key and **persisted before** Checkout; refuses `409 already_subscribed` if a subscription can charge. Returns `{ url }` (hosted Checkout, subscription mode, configured price, `client_reference_id` = owner) |
| `POST /billing/portal` | user (also while erasure is pending) | Portal for the owner's own stored customer; `409 no_billing_account` if none |
| `POST /billing/refresh` | user | re-reads the provider and commits (use after returning from Checkout; the redirect itself proves nothing) |
| `POST /billing/webhook` | Stripe signature | `express.raw` on the untouched bytes → `stripe.webhooks.constructEvent`; `400 invalid_signature` / `wrong_mode` / `invalid_event`; `503/500` are retryable |
| `GET /readiness` | user | gains `billing: { required, entitled }` |

Webhook events used: `checkout.session.completed`, `customer.subscription.created|updated|deleted|paused|resumed`, `invoice.paid`, `invoice.payment_failed`,
`invoice.payment_action_required` (others are acknowledged and ignored). The event only identifies WHICH customer to re-read: the owner comes from the persisted customer
binding (an unbound customer is ignored; metadata/`client_reference_id` may corroborate but never establish).

## Reconciliation and entitlement

1. `wiz_billing_lease` takes a persistent per-owner lease (30 s, fence counter) — PostgREST calls are separate transactions, so a DB lock cannot span the provider call.
   A concurrent reconciler gets `503 billing_busy` (Stripe retries). A committed duplicate event returns without any fetch.
2. The API fetches the CURRENT subscriptions of the bound customer (`subscriptions.list`, `latest_invoice` expanded) — never the event payload.
3. `wiz_billing_commit` verifies the lease, inserts `(mode, event_id)` and updates the entitlement in ONE transaction; any failure rolls both back (retry is safe). A stale
   holder whose lease expired is refused (`billing_lease_lost`), so an older snapshot can never overwrite a newer one.

Access = status `active` AND a verified paid period not yet ended (database clock). "Verified paid" (checked against the installed SDK 23 types; the list call expands
`data.latest_invoice` and `data.latest_invoice.payments`): the latest invoice is `paid`, in this Stripe mode (`livemode`), in the configured currency, for this customer,
generated by THIS subscription (`parent.subscription_details.subscription`), with `amount_paid > 0` and **`amount_paid_off_stripe` absent or 0** (out-of-band payments
report `amount_paid > 0` too, so `amount_paid` alone proves nothing), at least one `InvoicePayment` that is `paid`, backed by a `payment_intent`/`charge` (not a
`payment_record`), with money, in the configured currency and pointing at this invoice, and an invoice line whose period ends exactly at the item-level
`current_period_end` (the paid-through time). Anything missing or unverifiable (e.g. `payments` not present) is denied. Trials, incomplete, past_due, unpaid, paused, canceled,
conflicting (two live subscriptions / extra items / quantity ≠ 1), unknown statuses and foreign prices never grant. Cancel-at-period-end keeps access only to the verified
paid time. No grace period. An immediate cancellation (e.g. by the erasure `cancel` policy) ends access at once. The real-Stripe TEST run must confirm that a genuine
renewal invoice satisfies every one of these conditions (the period-line and payments conditions are the ones to watch).

## One open purchase per owner

Under the owner lease, Checkout first lists the customer's OPEN Checkout sessions at Stripe (so the identity of "the open purchase" survives restarts, workers and hours;
the idempotency key is per-call only). A session that is subscription-mode, referenced to this owner, for the configured price, with a URL and more than 5 minutes left is
reused (the longest-lived one if several); every other open session of that customer is expired, and Stripe is re-listed to confirm none other can still be completed.
Only then, if none was reusable, one new session is created. A subscription that can already charge refuses a second purchase (`409 already_subscribed`).

## Paid gate

Paid launch, no free tier: every value-adding saved-data WRITE needs an entitlement (`402 subscription_required`, nothing stored). Before any append/retrieval/provider work:
`POST /sessions/:id/chat`, `POST /sessions/:id/start`, legacy `POST /api/chat`. POST/PUT/PATCH on: goals, journal, reports, profile evidence (incl. confirm), training,
session checkpoints, saved messages (`POST /sessions/:id/messages`), career development records and attachments (`/career-plan`, `/learning-profile`, `/portfolio`,
`/prior-learning`, `/networking`, `/support-map`, `/pulses`, `/attachments`). Open without payment: signup/login/password, profile, onboarding, consent, Terms, notices,
billing, empty session creation and rename/archive, every GET (history reading), every DELETE (including saved records and sessions), `…/ai-use` switches, export, erasure.
Order: adult → paid → Terms/health → save_chats. The UI asks (Account → Subscription) instead of dead-ending.

## Export and erasure

Export gains `billing: { entitlements, events }` (the owner's own rows; no lease internals, no payloads). Erasure never orphans a charging subscription: before the account
closes, and again before the identity is removed, it takes the SAME owner lease as purchase (so checkout and erasure never interleave: the loser gets a retryable
`503 billing_busy`) and asks the provider about the customer. An established subscription that can still charge follows the owner policy: `block` (default) answers
`409 subscription_active` (or `erasure_incomplete`/`subscription_active` for a pending erasure; the portal stays reachable so it can be cancelled), `cancel` cancels it at the
provider first and verifies. An UNCOMPLETED purchase is not a policy question: its open Checkout sessions are expired and re-listed to confirm none can still be completed,
then subscriptions are checked once more in case one completed during the expiry (that one is then an established subscription, so the owner policy applies). Nothing can be
completed afterwards, so no unbound charging subscription is left; a late webhook for the erased customer is ignored. If the provider cannot be asked, erasure waits. Local billing
rows are removed with the account (foreign-key cascade). Only this customer's sessions are touched; nothing is deleted at Stripe and no retention period is assumed.
